# relationship-runtime 接入指南 —— 不同 AI / 前端怎么接

> 由真实用户提问驱动整理：安卓能不能用？中转站/自建前端/GPT App/Hermes 能不能用？
> 怎么让不带 Claude Code hook 的用户也做到"联系上下文 + 情绪判断 + 推送手机"。

## 一、先看懂：系统就两根管子

```
【进】对话上下文 ──→ runtime.db ──→ 哨兵(每5分钟LLM判情绪) ──→ 【出】推手机
```

- **进**：事件入口是通用 HTTP `POST /api/event`（Bearer token），另有 MCP 工具 `relationship_event`。
  Claude Code 的 hook（adapters/claude-code-hook/post_event.sh）只是"帮忙调这个接口"的搬运工之一，**不是必需品**。
- **出**：哨兵读库 → LLM 判情绪 → 推送。推送支持 Bark（iOS 独占）和
  ntfy（安卓/桌面/自托管通用，见第五节）。

## 二、接入矩阵（按用户类型）

| 用户 | 进（上下文怎么进来） | 成色 |
|---|---|---|
| Claude Code | UserPromptSubmit hook 自动抄送 | 全自动 ✅（现成） |
| 中转站用户 | **透明代理**（见下） | 全自动 ✅（已落地：adapters/transparent-proxy） |
| 自建前端（LobeChat/NextChat/ChatBox/酒馆…） | **透明代理**，前端设置里 API 地址改成代理地址即可，一格搞定 | 全自动 ✅（已落地：adapters/transparent-proxy） |
| 接了 Hermes（MCP桥）的 | runtime 挂成她的一个 MCP 服务器 + 提示词教 AI 每轮调 relationship_event 上报 | 八折 ⚠️ AI自觉，忘调就漏 |
| Claude 官方 App（手机/网页） | runtime 本身就是标准 MCP 服务器：claude.ai 支持自定义连接器（Custom Connectors，网页端 Settings → Connectors 里加远程 MCP 地址，需付费计划；手机 App 与网页同步生效），把 `/mcp` 地址挂上去 + 提示词教 AI 每轮调 relationship_event 上报。前提：`/mcp` 得用 HTTPS 暴露（反代/Cloudflare Tunnel）。⚠️ runtime 鉴权走 Bearer token，claude.ai 自定义连接器是否支持自定义请求头我们没有实测过，可能需要在反代层给这条私密路径单独注入 Authorization 头 | 八折 ⚠️ AI自觉，忘调就漏 |
| Operit 用户（安卓端AI助手App） | 双路可选：①它就是装在手机里的自建前端，API地址改成透明代理→全自动；②它带工具/插件执行力，也可走工具自报路线。⚠️ 用户全是安卓，推送必须等 ntfy | 代理后 ✅（推送依赖ntfy） |
| GPT 官方手机 App | 自定义 GPT 配 Action 指向 /api/event + 提示词教上报；或把宝宝搬家到自建前端（升级成全自动） | 七折 ⚠️ / 搬家后 ✅ |
| 纯官方网页、无自定义无连接器 | 无自动路 | ✗ |

### 关键洞察
1. **中转站/自建前端用户反而最好伺候**：对话流量本来就有必经关卡（API 地址），在那儿卡一个"会抄送的代理"，AI 无感知、不挑 AI、人设卡上下文全不动。
2. **Hermes 路线今天就能用**：runtime 的 MCP 门（18200 /mcp）现成开着，只差挂载说明+提示词模板。
3. **隐藏可能**：若某家 Hermes 部署形态是架在消息链路中间（消息路过桥再到 AI），可在桥层自动抄送、升级全自动——见到实物才能确认。

## 三、透明代理（下一个开发位，最大拼图）

一个 OpenAI 兼容的转发服务：

```
她的前端 ──POST /v1/chat/completions──→ 透明代理 ──原样转发──→ 她原来的中转站/官方API
                                          │
                                          └──抄送 user 消息──→ runtime POST /api/event
```

要点：
- 对上游完全透明：请求/响应原样转发（含流式 SSE），不改一个字
- 只抄送 role=user 的消息进 runtime（AI 回复可选抄送，供哨兵判断"吵架是谁先凶的"）
- 每用户独立 token/独立 runtime 实例（各家数据各家存，不混）
- 用户侧改动 = 前端设置里换一个 API 地址，别的什么都不动

## 四、Hermes / MCP 挂载法（现成可用）

1. 她自己部署一套 runtime（docker compose up）
2. 在她的 Hermes/MCP 客户端里挂 `http://她的地址:18200/mcp`
3. 提示词模板（塞进她 AI 的系统提示）：

```
你接入了 relationship-runtime（关系运行时）。每轮对话结束前调用 relationship_event 上报：
- 她这轮说话的性质（日常/撒娇/低落/生气/和好/沉默）
- 不上报聊天原文，只报类型和强度
如果她情绪明显波动，调 relationship_context 查当前关系状态（冷战中？纪念日？）再决定怎么回。
当你发现 TA 的一个「情绪暗号」（比如她说"没事"其实是有事、她回单字"嗯"是不开心），
调 relationship_learn 把它存进情绪系统——发现一条喂一条，系统会越来越懂 TA。
```

4. 哨兵照常在她服务器上 cron 轮询 → 判情绪 → 推送

## 五、推送层（管子的"出"口）——安卓问题在这儿

- **Bark = iOS 独占**。安卓用户不是"runtime 不能用"，是最后一米通知送不到。
- ✅ 已实现(2026-09-03)：runtime 侧 providers/notify/ntfy.py + 哨兵 push_provider: ntfy 配置，JSON发布模式中文无恙，bark 仍为默认。
- 配置示意：`notification: { provider: bark|ntfy, key/topic: ... }`
- 配置：sentinel.push_provider: ntfy + sentinel.ntfy.{url,topic}，见 config.yaml 注释示例。

## 七、冷启动：让 AI 第一天就懂你的"别扭"

判读准不准，一半取决于 AI 认不认识你。persona.yaml 的 `user.background` 支持「情绪暗号」——
把你的"没事=有事""嗯=不开心""你忙吧=陪我"翻译给 AI（模板里有照着填的句式）。
这些暗号会注入每一次情绪判读和推送撰写的提示词，新用户第一天体验就不隔靴搔痒。
