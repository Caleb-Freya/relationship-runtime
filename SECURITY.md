# Security Policy

Relationship Runtime holds some of the most personal data a piece of software
can hold: what someone said, when they left, how they were feeling, sometimes
how they slept. We take reports about it seriously.

## Supported versions

| Version | Supported |
|---------|-----------|
| 0.1.x   | ✅ |
| < 0.1   | ❌ |

This project is pre-1.0. Security fixes land on the latest 0.1.x release; please
upgrade before reporting an issue against an older build.

## Reporting a vulnerability

**Please do not open a public issue for a security problem.**

Report it through GitHub's private vulnerability reporting: go to the
repository's **Security** tab → **Report a vulnerability** (GitHub Security
Advisories). That channel is private between you and the maintainers until a fix
is published.

Helpful things to include:

- What the issue is and where in the code it lives
- Steps to reproduce, or a proof of concept
- What an attacker gets out of it (read relationship data? send pushes as the
  AI? reach the host?)
- Your deployment shape: direct Python, Docker, behind a reverse proxy or tunnel

What to expect:

- An acknowledgement of your report, and a first assessment once we've had a
  look
- Updates as we work on a fix, and credit in the release notes if you'd like it
- Coordinated disclosure — we'll agree a public advisory with you rather than
  publishing before you're ready

Please don't include real personal data (real chat logs, health records, tokens,
push keys) in a report. Redact it or fabricate an equivalent.

## In scope

- Authentication bypass on the MCP endpoint or the HTTP API (anything reachable
  without a valid `Authorization: Bearer <mcp.token>` that shouldn't be)
- Leaking relationship, message, or health data — including data escaping into a
  push body when the contract says it must not (`health_sensitive` details and
  explicit content are hard constraints, see [docs/contract.md](docs/contract.md))
- Path traversal, injection, or remote code execution in the runtime, the setup
  page, or the adapters
- The transparent proxy adapter forwarding credentials or conversation content
  somewhere it shouldn't

## Out of scope

- A deployment the operator deliberately exposed to the public internet without
  a reverse proxy and auth (see the security notes in the [README](README.md))
- Weak `mcp.token` values chosen by hand instead of the random one generated by
  `scripts/init.sh`
- Vulnerabilities in third-party services you point the Runtime at (Bark, ntfy,
  your LLM provider) — report those to them
- Someone with physical or shell access to the host reading `data/runtime.db`;
  the database is local and unencrypted by design

## Protecting your own deployment

- **Listen locally by default.** `mcp.listen` is `127.0.0.1:18200`, and the
  provided `docker-compose.yml` binds the host port as `127.0.0.1:18200:18200`.
  Keep it that way unless you have a reason not to.
- **Never expose the port raw.** If real public traffic must reach the Runtime,
  put a reverse proxy or tunnel in front (Nginx / Caddy / Cloudflare Tunnel) and
  require the Bearer token on every request.
- **Treat `mcp.token` as a password.** It is the key to your relationship data.
  Use the random one from `scripts/init.sh`, hand it only to clients you trust,
  and rotate it (delete it from `config.yaml` and regenerate) if you suspect
  exposure.
- **These files contain private data and must never be committed:**
  `config.yaml`, `persona.yaml`, `profile.yaml`, `data/` (the SQLite database
  and the shadow outbox), `adapters/transparent-proxy/proxy-config.json`, and
  `.env`. They are already listed in `.gitignore` — run `git status` before you
  commit anyway, and never paste their contents into an issue, a screenshot, or
  a chat with a third-party service.
- **Shadow Mode is there if you want it.** The default is `live` (the service
  really sends once a push channel is configured). Setting `runtime.mode:
  shadow` sends nothing to a real device, which also means a misconfiguration
  can't message someone on your behalf while you're still setting up. Switch
  back to `live` whenever you're ready.
